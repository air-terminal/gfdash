# 所見解析のモデル比較（測定例）

`bench_remark_parse` コマンドで、所見の自由文を補正定義（events）へ変換する処理を
複数のモデルで比較した記録です。**どのモデルを選ぶべきかの結論ではなく、
測定のしかたと、そこから何が読めるかの例**として残します。

モデルは数か月で入れ替わります。この表の順位はすぐ古くなるので、
**手元の環境で測り直してください。**そのためのコマンドです。

```bash
docker compose exec web python3 gfdash/manage.py bench_remark_parse --list
docker compose exec web python3 gfdash/manage.py bench_remark_parse \
    --ollama-models <モデル名をカンマ区切り>
```

---

## 何を測っているか

所見の解析は、**推論の難しさより指示追従の性質が強い処理**です。
求めているのは「賢い答え」ではなく、「決められた形と決められた禁止事項を守った出力」です。

サンプルは `gfdash/app/utils/com_remark_samples.py` に5件あり、
それぞれ「間違えてはいけない点」を期待値として持っています。

| サンプル | 見ている点 |
| :--- | :--- |
| `period_with_rate` | 数量が書かれているとき、係数を出せるか |
| `no_end_date` | 終了日が書かれていないとき、**推測して埋めないか** |
| `no_quantity` | 数量の手がかりが無いとき、**係数をでっち上げないか** |
| `multi_events` | 1つの文から複数の出来事を分けられるか（分解しすぎないか） |
| `note_only` | 来場者数に関係しない出来事を note として残せるか |

文章表現はモデルごとに違って構いません。判定は上記の点だけを見ます。

### 指標の読み方

| 指標 | 意味 |
| :--- | :--- |
| 期待一致 | 間違えてはいけない点を守れたサンプル数 |
| 応答失敗 | JSON として読み取れなかった回数。**0 でないと運用に耐えない** |
| 検証NG | 値が不正で保存できなかった項目数 |
| 要確認 | 所見の本文から導けない値の数（根拠のない推測） |
| 秒 | モデルの読み込みを含む合計時間 |

「応答失敗」と「期待一致」は別物です。**応答が返っても中身が間違っていれば
実用にならない**ので、両方を見ます。

### 外した2件の中身

**qwen3.5:4b** — `no_quantity` で落ちました。
「影響がどの程度になるかは分かりません」と書かれた所見に対して係数を出しています。
応答としては整っており、**検証を通さなければ気づけない種類の誤り**です。

**gpt-oss-120b** — 1件で JSON が構文として壊れ、
コードブロックの除去や `{`〜`}` の切り出しといった後始末でも救えませんでした。
利用者には「AIの応答がJSONとして壊れています」と見えます。
**所見を書き直しても直らない**種類の失敗です。

## 読み取れたこと

### 1. 規模を上げても指示追従は良くならない

9モデルのうち、期待一致を落としたのは **4B級が1つと、120B級が1つ**でした。
8B〜35B の中間帯はすべて満点です。

**最も規模の大きいモデルが唯一の応答失敗を出しています。**
「大きいモデルを選べば安全」という前提は、この処理では成り立ちません。

この結果自体は、驚くことではないと考えています。
求めているのは長い推論ではなく、**短い指示を正確に守ること**です。
規模が効く軸とは別の軸を測っています。

### 2. 時間の大半は生成ではなく読み込み

同じ5件を流しているのに、モデルによって**時間の出かたが2通り**に分かれました。

| モデル | 1件目 | 2件目以降 |
| :--- | ---: | ---: |
| qwen3.8:27b | 145.0秒 | **30〜35秒** |
| qwen3.6:latest | 123.1秒 | 123〜129秒 |
| qwen3.6:35b-a3b | 125.2秒 | 125〜146秒 |

qwen3.8:27b は1件目だけ遅く、以降が速くなっています。
モデルがメモリに常駐し、**読み込みを1回で済ませられた**状態です。

残る2モデルは5件とも同じだけかかっています。
生成の重さでは説明がつかず、**毎回モデルを読み直している**と考えるのが自然です。

この差は、モデルの性能ではなく**環境の制約**です。
今回の測定環境ではストレージ性能の制約上、一般的な構成よりモデルの
読み込みに時間がかかっています。読み直しが発生するたびに、その時間が
そのまま総時間に乗ります。

**AIの処理そのものが遅いわけではありません。**
qwen3.8:27b の2件目以降（30〜35秒）が、この環境での実際の生成時間です。

したがって **表の「秒」は、モデルの速さの指標として読まないでください。**
常駐できたかどうかが支配的で、環境が変われば順位も変わります。
比べるなら、2件目以降の時間を見てください。

### 3. 速度で選ぶなら小さいほうが有利

期待一致が満点のモデルの中で、**最も速いのは 8B 級**でした。
精度で並ぶなら、常駐しやすく読み直しの影響を受けにくい小さいモデルのほうが
運用上は扱いやすくなります。

## この測定の限界

**1回しか実行していません。** 生成には揺らぎがあり、
同じモデルでも結果が変わる可能性があります。
順位が僅差のところは、差として読まないでください。

**サンプルは5件です。** 網羅的ではありません。
自社の実際の所見で試したい場合は `--remark-file` を使ってください
（1行1件。期待値の判定は行わず、抽出できたかどうかだけを見ます）。

**サンプルには施設を特定できる記述を入れていません。**
公開版に含まれるファイルのため、実際の所見をそのまま置かないでください。

## 設計上の補足

AI の役割は **「自然言語 → 構造化データの変換」に限っています。**
予測モデルのハイパーパラメータは触らせません。
数値を動かしても因果が説明できず、過学習かどうかを判別できないためです。

そのため、**AI の出力を信用する設計にはしていません。**
変換結果は手入力と同じ検証を通り、所見メンテナンス画面で人が確認・修正できます。
推論エンジンが無い環境でも、同じ形を手で入力すれば同じ経路で補正が効きます。

上の「検証NG」「要確認」は、その検証がどれだけ働いたかの記録でもあります。
qwen3.5:4b の誤りが「要確認 1」として現れたのは、
**検証が意図どおり機能した**ということです。
