# AI予測・レポート

来場者数の予測（Prophet）と、月次レポートの自動生成（ローカルLLM）についての
セットアップと使い方です。

**この機能は任意です。** 推論エンジンを用意しなくても、集計・分析の各画面は
そのまま使えます。予測だけを使い、レポートを使わないこともできます。

| 画面 | 内容 |
| :--- | :--- |
| 来場者予測推移（410） | 日別の来場者予測とレポートの表示 |
| 予測実行履歴比較（415） | 過去の予測実行を並べて比較する |
| 月次所見入力（480） | 運営上の出来事を書き、補正の定義へ変換する |
| 所見メンテナンス（485） | 変換された補正定義を確認・修正する |
| AIバッチ手動実行（490） | 予測とレポート生成をその場で実行する |

予測の区分は「平年通り」「天候が良い場合」「天候が悪い場合」の3本です。

**予測の精度は検証中です。** 機能としては安定していますが、所見による補正がどの程度
精度を改善するかは、月ごとに `evaluate_forecast` で実績と突き合わせて確かめている
段階です（後述「精度の検証」）。予測値は参考値として扱ってください。

---

## 1. 推論エンジンを用意する

レポート生成と所見の解析にローカルLLMを使います。推論エンジンは2つの方式に
対応しています。どちらか一方を用意してください。

| 方式 | `LLM_PROVIDER` | 対象 |
| :--- | :--- | :--- |
| Ollama ネイティブAPI | `ollama`（初期値） | Ollama |
| OpenAI互換API | `openai` | llama.cpp server / vLLM / LM Studio / [FreeToken](https://github.com/FlashML-org/FreeToken) など |

### A. Ollama を使う場合

ローカルにOllamaをインストール・起動し、あらかじめ対象のAIモデルをPull（ダウンロード）しておきます。

```bash
ollama pull gemma4:e4b
```

*(※別のモデル、例えば `qwen2.5:7b` などを使用する場合は、そちらをPullしてください)*

### B. OpenAI互換APIの推論エンジンを使う場合

お使いのエンジンの手順に従って起動し、モデルを読み込んでおきます。導入方法は
製品ごとに異なるため、本システムでは扱いません。本システムが必要とするのは
**OpenAI互換のエンドポイントのURLだけ**です。

起動できたら、接続できるか事前確認しておくとトラブル時の切り分けが楽になります。

```bash
curl http://localhost:8080/v1/models
```

モデルの一覧がJSONで返れば準備完了です。この `/v1` までのURLを
`OPENAI_API_BASE` に設定します。

なお、**コンテキスト長は推論エンジン側の設定に従います**（画面やパラメータからは
指定できません）。必要な場合はエンジンの起動オプションで調整してください。
思考（thinking）は切り替えられます（`OPENAI_THINK_PARAM`）。

## 2. 設定項目

`.env`（または `gfdash/settings.py`）を環境に合わせて調整します。

### 必ず変更するもの

* **`DISABLE_BATCH_EXECUTION`**: AIバッチ処理（予測やAIレポート生成など）の無効化フラグです。初期値は安全のため `True`（無効）になっています。実際にAI機能を利用する際は、必ず **`False`** に書き換えてください。

### 接続先

* **`LLM_PROVIDER`**: 使用する推論エンジンのAPI方式（初期値: `ollama`）。
  * `ollama` … Ollama のネイティブAPIを使います。従来どおりの動作です。
  * `openai` … OpenAI互換APIを使います。[FreeToken](https://github.com/FlashML-org/FreeToken) / llama.cpp server / vLLM / LM Studio など、OpenAI互換のエンドポイントを提供する推論エンジンで動作します。
  * 互換API側では**コンテキスト長をリクエストで指定できません**（推論エンジン側の設定に従います）。該当する入力欄は画面上で無効化されます。思考の切り替えは下記の `OPENAI_THINK_PARAM` で送れます。
* **`OPENAI_API_BASE`**: OpenAI互換APIの接続先（`LLM_PROVIDER=openai` のとき）。`/v1` まで含めて指定します。
* **`OPENAI_API_KEY`**: 同上の認証キー。ローカルの推論エンジンでは不要なことが多く、空のままで構いません（空の場合は認証ヘッダを送りません）。
* **`OPENAI_THINK_PARAM`**: 思考（thinking）の切り替えをどの項目で送るか（初期値: `chat_template_kwargs`）。OpenAI互換を名乗る推論エンジンでも、受け付ける方言が違うため選べるようにしています。

  | 値 | 送る項目 | 対象 |
  | :--- | :--- | :--- |
  | `chat_template_kwargs` | `chat_template_kwargs` の `enable_thinking` | FreeToken / vLLM / SGLang / llama.cpp server |
  | `reasoning_effort` | `reasoning_effort` | OpenAI 方言。本家 OpenAI の推論モデルもこれ |
  | `thinking` | `thinking` の `type` | DeepSeek 方言 |
  | `off` | 何も送らない | 推論エンジン側の設定に従う |

  * 未知の項目を拒否するサーバに接続して 400 が返る場合は `off` にしてください。`off` にすると画面の思考の入力欄も無効になります。
  * 思考そのものの有無は、推論エンジンによらず `OLLAMA_PRESET` / `OLLAMA_THINK` で指定します。
  * 思考に対応しない銘柄に送っても害はありません（チャットテンプレートは未知の変数を無視します）。
* **`OLLAMA_API_URL`**: Ollamaが動作しているエンドポイントのURLを指定します（`LLM_PROVIDER=ollama` のとき）。
  * **DockerコンテナからホストのOllamaを叩く場合**: `'http://host.docker.internal:11434/api/generate'` (初期値)
  * **Dockerを使わず、ローカルPC上で直接システムを実行する場合**: `'http://localhost:11434/api/generate'` に書き換えてください。
* **`OLLAMA_MODEL`**: 使用するAIのモデル名を設定します（初期値: `'gemma4:e4b'`）。方式に関わらず、この項目でモデルを指定します。

### 実行パラメータ

* **`OLLAMA_PRESET`**: AI実行パラメータのプリセット（初期値: `standard`）。通常はこれだけを指定すれば十分です。

  | 値 | 用途 | num_ctx | タイムアウト | 思考 |
  | :--- | :--- | ---: | ---: | :---: |
  | `standard` | 通常はこれ | 4096 | 300秒 | 無 |
  | `long_running` | タイムアウトする場合 | 4096 | 1800秒 | 無 |
  | `low_memory` | モデルが読み込めない、極端に遅い場合 | 2048 | 900秒 | 無 |
  | `high_context` | より多くの実績データを渡したい場合 | 8192 | 900秒 | 無 |
  | `thinking` | 多段の推論をさせる場合 | 16384 | 1800秒 | 有 |

  * 下記の個別設定を書いた場合は、そちらがプリセットより優先されます。プリセットで運用する場合は個別設定をコメントアウトしてください。
  * AIバッチ実行画面(490)からは、実行のたびに一時的に変更することもできます。
  * **レポートのエンジンは自分に合った既定を持ちます。** 多段版（`staged`）のまとめの段は thinking を使うため、何も指定しなければ `num_ctx=16384` / thinking ON で動きます（段1〜3は thinking を使いません）。段4のプロンプトは 2,000 トークン前後あり、26B 級の thinking は 6,000〜10,000 トークン使うので、8192 では本文の余地が残りません。優先順位は「490画面・コマンド引数 ＞ `.env` の明示指定（`OLLAMA_PRESET` または個別設定）＞ エンジンの既定 ＞ `standard`」です。`.env` に `OLLAMA_PRESET=low_memory` のような機械の制約を書いていれば、エンジンの既定より優先されます。490画面はモードを切り替えると既定を表示に反映します（ダイアログで値を決めた後は変えません）。

* **`OLLAMA_TIMEOUT`**: タイムアウト秒数（初期値: プリセットの値）。CPU実行時などレポート生成に時間がかかる場合は、`600` など長めの値を設定してください。
* **`OLLAMA_NUM_CTX`**: AIが確保する記憶領域のトークン数（初期値: `4096`）。値を上げるとより多くの実績データをプロンプトに含められますが、VRAMの使用量も増えます。モデルが読み込めない場合は `2048` などに下げてください。
  * **`LLM_PROVIDER=openai` では使用されません。** 推論エンジン側の設定に従います。
  * 適切な値はVRAM容量だけでは決まりません。同じ容量でも、小さなモデルなら余裕があり、大規模なモデルでは本体だけでほぼ埋まります。AIバッチ実行画面(490)に症状から選べるプリセットを用意しているので、そちらもご利用ください。
  * 490画面の実行パラメータでは、スライダー（4096〜65536 を 4096 刻み）と数値入力のどちらでも指定できます。刻みに合わない値は数値入力で入れてください。
* **`OLLAMA_THINK`**: 思考（thinking）を有効にするかどうか（初期値: `False`）。
  * `LLM_PROVIDER=openai` でも使われます。送る項目は `OPENAI_THINK_PARAM` で選びます（`off` のときだけ送りません）。
  * 思考に対応したモデルを使う場合のみ意味を持ちます。非対応のモデルには送信されません。
  * **有効にする場合は `OLLAMA_NUM_CTX` も併せて広げてください。** 思考は与えられたコンテキストを埋めるように消費するため、余裕が無いと本文が生成されないまま終わります（レポートが空になります）。`LLM_PROVIDER=openai` ではコンテキスト長を指定できないので、推論エンジン側で「プロンプト＋思考＋本文」が収まる長さを確保してください。
  * 軽量版（`single`）と予測レポートは集計済みの数値を定型の見出しに沿って記述するもので、多段の推論を必要としません。そのため初期値では無効にしています。多段版（`staged`）のまとめの段だけはエンジンの既定で有効になります（上記）。
  * **`LLM_PROVIDER=openai` で thinking を使う場合**、推論エンジンの起動時に「プロンプト＋thinking＋本文」が収まるコンテキストを確保してください。`/v1/models` が返す `max_model_len` はモデルの素の能力で、実行時に確保した量とは限りません。足りないと終了ステータスが `truncated (length)` になります。
* **`LLM_THINK_EFFORT`**: thinking の強さ（初期値: 空＝指定しない）。`low` / `medium` / `high` / `max` のいずれか。thinking が ON のときだけ意味を持ちます。

  | 推論エンジン | 送る項目 |
  | :--- | :--- |
  | Ollama | `think` に強さの文字列（`think: "high"` のように送る） |
  | OpenAI互換 | `reasoning_effort` に強さ。`OPENAI_THINK_PARAM=chat_template_kwargs`（既定）でも、強さを指定したときだけ `reasoning_effort` に切り替えます（`enable_thinking` は真偽しか載せられないため） |

  * 空のままなら従来どおり ON / OFF だけを送ります。
  * **強さを持たない銘柄では無視されます。** Ollama はエラーを返さず、従来どおり思考します。
  * 思考の長い銘柄（Qwen 系など）で生成が遅いときに `low` を試す、といった使い方を想定しています。
  * 490画面の実行パラメータでは、thinking を ON にしたときだけスライダーが現れます（左端は「指定しない」）。

## 3. 動かしてみる

すべてのデータ投入とAIの準備が完了したら、予測・レポート作成処理をテストします。
ブラウザの画面から実行する方法と、コマンドラインから実行する方法があります。

### A. ブラウザ画面から実行する

管理者アカウントでログインし、**「AI予測分析」 → 「AIバッチ手動実行」**（490）を開きます。
ボタンを押すと、バックグラウンドで予測計算やレポート生成が実行され、
ダッシュボードに結果が反映されます。

*(※実行する前に `DISABLE_BATCH_EXECUTION` を `False` に書き換えておく必要があります)*

### B. コマンドラインから実行する

cron へ組み込む場合はこちらを使います。

#### ① Prophetによる来場者数予測

```bash
python manage.py run_forecast --periods 30
```

| オプション | 内容 |
| :--- | :--- |
| `--periods <整数>` | 予測する未来の日数（初期値: `30`） |
| `--output <ファイル名>` | 外部連携用に出力するJSONのファイル名（初期値: `forecast.json`） |
| `--note <文字列>` | 実行履歴に残すメモ。比較画面（415）で実行を見分ける目印になる |
| `--from-ym <YYYY-MM>` | 指定した月の1日から予測をやり直す（学習を前月末までに限定）。月の途中で実行しても、その月全体が予測になる（`--periods` がその月の日数に満たなければ月末まで延ばす）。補正の効果を比べるときに基準をそろえる用途 |

`--from-ym` の月によって、結果の行き先が変わります。

| 起点 | 扱い | 実行履歴（415で比較） | 最新予測（101・ラズパイ同期） |
| :--- | :--- | :--- | :--- |
| 実行月以降 | 最新予測の更新 | 残す | **置き換える** |
| 実行月より前 | 過去の打ち直し | 残す | **触らない** |

過去の月を打ち直す目的は精度の評価です。運用中の最新予測を古いデータで学習した予測で
置き換える理由が無いため、履歴だけを残します。`evaluate_forecast --runs <ID>` でその月を
評価できます。

**計画休業の反映について:**
休業・祝日カレンダー（画面913）で「計画」として登録された時間帯休業は、
予測値に営業時間ぶんの補正が掛かります。終日休業なら 0 になります。
補正の割合は自社の過去実績から自動で算出されるため、設定は不要です。
実績が少ない環境では時間帯の単純按分にフォールバックします。

台風接近などの天候起因で登録された休業は、将来について予見できないため
補正の対象外です。この区別は `temp_closed` のビットで行っています
（[codes.md](codes.md) を参照）。

#### ② ローカルLLMによるレポート生成

```bash
python manage.py run_llm_analysis --mode review
```

| オプション | 内容 |
| :--- | :--- |
| `--mode <review \| forecast_1m \| forecast_3m>` | **【必須】** レポートの種類。`review`:当月のレビュー / `forecast_1m`:翌月の予測 / `forecast_3m`:3ヶ月先までの予測 |
| `--ym <YYYY-MM>` | 分析・予測の基準となる年月（初期値: 実行時の当月） |
| `--model <モデル名>` | 一時的に別のモデルを指定して実行する |
| `--stream` | 生成の様子をコマンドライン上にリアルタイム表示する |
| `--dry-run` | AIを呼ばず、組み立てたプロンプトを表示して終了する。履歴も残さない。文面の確認や、推論エンジンの無い環境での動作確認に |
| `--review-engine <single \| staged>` | レビューのエンジンを一時的に切り替える（後述）。同じ月を両方で作って読み比べる用途 |

#### レビューレポートの2つのエンジン

レビュー（`review`）は、`.env` の `LLM_REVIEW_ENGINE` で作り方を選べます。

| エンジン | 渡すデータ | 生成回数 | 向く場面 |
| :--- | :--- | :--- | :--- |
| `staged`（既定） | 週別・日の区分別（平日／土日／祝日／第2休日カレンダーごと。時間帯の内訳つき）の前年比、連休・特別営業・第2休日の期間平均、営業時間内の雨（長さ・強さ・時間帯）と強風・猛暑日・冬日・雪の日の平均、休業の印、客層の前年同月比、確定済みの所見 | 4回 | 月の中の動き（連休で伸びた、後半に失速した、雨の日に落ちた）まで読ませたいとき |
| `single` | 月の合計値だけ | 1回 | 軽い機械、短時間で済ませたいとき |

多段版は同じ月を3つの角度（来場者推移・天候・外部要因）で別々に読ませ、最後にまとめます。
各段は互いの出力を見ず、まとめの段だけが統合します。**数値表と比較（前年比・群ごとの平均・差）は
プログラムが組み立て、AIには「そのまま使う」と指示します。** AIに集計や比率の計算をさせると
数値が変わるためです。日別の表は渡しません。渡すと日付を列挙して終わり、週や期間の
まとまりで語らなくなります。

週の予測比が ±10% を超えた週は、ずれの大きい日（最大3日）と、その日の事実（雨の時間と
時間帯・強い雨・雪・強風・休業や特別営業の印・休日カレンダー）を「予測とのずれ」として
来場者推移の段に渡します。どの日がずれを作ったかはデータで分かるので、AI に理由を想像させず
事実だけを述べさせます。予測は tz301 にある日別値（その日を最後に予測した実行の値）です。

期間のまとまりとして拾うのは次の3つです。休業の印がある日は平均の母数から除きます。

| 種類 | 拾い方 |
| :--- | :--- |
| 連休 | 土日と祝日（ta220 の祝日フラグ）が3日以上続いた区間。月をまたぐ連休も拾う |
| 特別営業 | 特別営業フラグが続いた区間 |
| 第2休日 | `ENABLE_HOLIDAY2=True` のとき、第2休日カレンダー（tz810）の休日が続いた区間。備考が名前になる |

日の区分は 平日／土日／祝日 に、第2休日カレンダーごとの区分が加わります。第2休日の区分は
レポート上では「カレンダーの名称＋休日」（名称は画面 913 で付けたもの）で出ます。重なりは 第2休日 ＞ 土日 ＞ 祝日
の順で、土日に重なった祝日は土日として数えます（月〜金の祝日だけが「祝日」）。第2休日カレンダーの
勤め先が祝日に稼働する場合、月〜金の祝日は土日と違う動きになるため分けています。

お盆や年末年始のように暦に無い期間は、第2休日カレンダーか所見に登録があるときだけ
レポートに現れます。

天候は**営業時間内**（tz901 code 005 の朝・昼・夜の時間帯。101 画面のテロップと同じ設定）の
時別値（tz105）で判定します。雨量の合計は使いません。来場に結びつくのは「どれだけの時間降ったか」
「どれだけ強く降ったか」「どの時間帯に降ったか」だからです。

| 材料 | 判定 |
| :--- | :--- |
| 雨のあった日 | 営業時間内に 1mm/h 以上の時間があった日。観察の材料には雨の時間数と降った時間帯を添える |
| 強い雨の日 | 営業時間内の最大時間雨量が tz901 code 006「やや強い雨」（既定 5mm/h）以上 |
| 時間帯別 | 朝・昼・夜ごとに雨の有無を持ち、その時間帯の来場者数で影響を測る |
| 強風の日 | 日最大瞬間風速（tz101）15m/s 以上で、かつ営業時間内の時別平均風速（tz105）6m/s 以上の時間があった日。発生したときだけ。施設に効くのは突風なので瞬間風速で見るが、日別値は時刻が分からず夏の雷雨の一瞬の突風まで拾うので、営業時間内の風で裏付ける。時別値が無い日は突風だけで判定。参考として、瞬間風速と風向に加えて**風が強かった時間帯・その中の最大平均風速と風向・その時間に降っていた雨量**を添える（施設の条件を同じ時刻の値どうしで照合できるように） |
| 猛暑日 | 最高気温 35℃以上 |
| 冬日・雪の日 | 最低気温 0℃未満／営業時間内に雪の時間が2時間以上あった日（1時間だけの小雪は数えない。001・101 画面で雪の印が付く日とほぼ一致する） |

強風・猛暑日・冬日・雪の日は、当月か前年に起きた月と、過去N年の同月平均が 1 日以上の月
（例年は起きる月）にだけ出します。季節の月を固定で持たないのは、地方によって雪の月も猛暑の月も
違うためで、自施設の蓄積がその地方の季節をそのまま表します。蓄積が無い初年度は、起きた月だけに
出ます。

**影響の測り方**: 天候に該当した日（時間帯）の来場を、**同じ日の区分（平日／土日／祝日／
カレンダー休日）でその天候に該当しなかった日の平均**と比べ、その比率を平均します。雨の日と
雨なしの日を単純に平均で比べると、雨が土日に集中した月は逆の結論になるためです。
時間帯別は当月だけ出します（前年と比べる項目ではありません）。

レポートに残る表は「気象の要約」だけです（気温の群 → 雨 → 雪 → 風の順。強い雨の日は当月・前年とも
0 なら出しません）。影響の数値は観察の材料にだけ渡し、文章で語らせます。

**例年との比較**: 気象の要約に「過去N年の同月平均」を添えます。気象庁の平年値には営業時間内の
雨や雨の時間数が無いので、自施設の蓄積（当月・前年を除く過去5年）から出します。蓄積が
2年に満たなければ列を出さず、前年との比較だけになります（1年なら前年同月と同じ値になるため）。
年数は必ず表示し、AI にも「過去N年の平均」と書かせます。時別値の無い年は、時別値が要る
項目（雨の日数・強い雨・雪）の平均に入れません。

時別値が無い日は tz101 の日別値に落とし、雨の有無だけを見ます（時間数と時間帯は不明）。
風向と施設の関係（特定の風向で一部の打席が使えない等）はシステムは知らないので、
`custom_prompts/review.txt`（施設プロファイル）に書いておくと、まとめの段が強風の日の材料と
結びつけて書けます。まとめの段には「条件のすべての要素を観察の数値で確かめてから当てる。
1つでも確かめられなければ触れない。別の時刻の値どうしを組み合わせない」と指示しています。
条件は1行に1つずつ書くと取り違えが起きにくくなります。雨の閾値と来場の関係は分かっていない前提で、結果を見て
code 006 の値を動かしてください。

レポートの見出しは「予測と実績・前年比較」「時間帯別の動向」「天候の影響考察」に
**「運営上の出来事」**（確定済みの所見の整理）と**「総括」**が加わり5つになります。
週ごとの動きと期間のまとまり（連休・特別営業・休日カレンダーの期間）は「予測と実績・前年比較」に、
朝・昼・夜と日の区分は「時間帯別の動向」に書き分けさせます。
最初の4つの見出しは「事実（観察の要約）」と「【分析総括】（観察どうしを結びつけた読み）」の
2段で書かれます。分析総括に持ち込めるのは観察と所見にある事実だけで、無い出来事や数値は
足しません。

thinking を使う段では、実行ログに `[thinking... 12,345文字]` の進捗が出ます。思考の中身は
流さず、同じ行を書き換えて文字数だけを伸ばします（中身は数万文字になり、ログが読めなくなるため）。
本文が始まると行が閉じ、続けて本文が流れます。

生成が4回になるぶん時間がかかります。1回の生成に `OLLAMA_TIMEOUT` が効くので、
最大でその4倍です。段の出力は実行ログ（490 の画面・コマンドの標準出力）に流れます。
1段でも本文が空なら中止し、レポートは保存しません。例外はまとめの段で、思考が上限に達して
本文が出なかった（終了理由が `length`）ときは、まとめだけ思考なしで1回やり直します
（段1〜3の出力はそのまま）。やり直したことはログと実行履歴のメモに残り、490 画面では終了後に
ダイアログで知らせます。ログには**1回目がどこで切れたか**（プロンプト・生成のトークン数と思考の
文字数）も出します。打ち切った上限は推論エンジン側にあり（Ollama は `num_ctx`、OpenAI互換は
起動時のコンテキスト長や銘柄ごとの思考の上限）、こちらからは値が見えないためです。
思考の長さはモデルによって大きく違い、コンテキストを広げても伸びるだけのことがあります。
まとめの出力に数値表が無ければ、
プログラムが最初の見出しの直後に差し込みます（AIが要約の指示に引きずられて表を落とすことがあるため）。
文章が引く数値の根拠として、週別・日の区分×時間帯・気象の要約の表も、観察と同じ数値から
プログラムが作り、生成後にそれぞれの見出しの下へ置きます。AIには表を作らせません。

| `.env` のキー | 既定 | 内容 |
| :--- | :--- | :--- |
| `LLM_REVIEW_ENGINE` | `staged` | `single` にすると軽量版 |
| `LLM_SAVE_STAGE_OUTPUT` | `False` | `True` にすると段ごとの出力も履歴（tz312）に残す。「まとめが何を元に書かれたか」を後から追える。月に4行ずつ増える |

レポート末尾の版表示は `run_llm_analysis v1.0.0 / prompt staged/v1.0.0` のように、
どのエンジンで作ったかが分かる形です。

レポートには次のルールが組み込まれています。

- 提供された数値以外のデータを作らない。書かれていない原因や出来事を推測して補わない
- **いかなる場合も、業務改善の提案・アドバイス・スタッフへの指示を出力しない。** 数値の分析と事実の総括のみ

提案を禁じているのは、提案の部分が最も想像で埋められやすく、そこが崩れるとレポート全体が
信用されなくなるためです。

#### 施設の情報をプロンプトに足す

`gfdash/custom_prompts/review.txt` に施設の情報（打席数・営業時間・天候による運用の制限など）を
書いておくと、レビューレポートのプロンプトの先頭近くに差し込まれます。
`review.txt.example` を同じ場所にコピーして書き換えてください。`review.txt` は
git の管理外なので、書いた内容が公開されることはありません。

ここに書くのは「いつでも変わらない施設の条件」だけにしてください。日付を持つ出来事は
月次所見（後述）に種別つきで登録します。このファイルの内容はどの月のレポートにも同じ文が
差し込まれるため、過去の月を作り直したときに、その月にはまだ無かった出来事を前提に
書かせてしまいます。

先行予測は `forecast_1m.txt` / `forecast_3m.txt` を同様に読みます。

## 4. 使い方

セットアップが済んだあとの、日常運用の流れです。画面は「AI予測分析」メニューに
まとまっています。

### 月次所見 — AIが知らない情報を渡す

競合店の開業、近隣の工事、設備の入れ替えなど、**実績データに現れる前から分かっている出来事**があります。これらは過去のデータから学習できないため、予測にもレポートにも反映されません。

**「月次所見入力」**（480）で、対象月を選び、タブで区分を切り替えて自由文を書きます。

| 区分 | 用途 | 使われる先 | 手順 |
| :--- | :--- | :--- | :--- |
| 予測所見 | これから先を見通すための情報 | 予測の補正と予測レポート | 保存 → AIで解析（または手で追加）→ 確定 |
| レビュー所見 | 済んだ月に実際に起きたこと | レビューレポートのみ | 保存 → 確定 |

レビュー所見は本文だけで、補正の設定はありません。起きたことは実績に出ているため、見立てを置く意味が無いからです。先の月に影響が続く出来事は、予測所見のほうに書いてください。

以下は予測所見の手順です。押せる順にしかボタンが有効にならないので、迷うことはありません。

**「AIで解析」** は自由文を補正の形へ変換します。イベントごとに種別・期間・影響の見立てを読み取り、表に並べます。

* 影響の見立ては「大きく増える（+20%）」〜「大きく減る（-20%）」から選びます。`%` で直接指定することもできます。係数は通常を `1.00` とした倍率で、幅は見立ての不確かさを表します
* 影響が読めない出来事は種別を「記録のみ」にします。レポートの材料にはなりますが、予測の補正には使われません
* **根拠・補足情報は必須です。** 半年後に妥当性を見直せるようにするためです

**確定した所見だけが予測とレポートに使われます。** AIが出した数値をそのまま予測へ流さないための一段です。

所見の本文から導けない値があると「要確認」が表示されます。たとえば所見に数量の記載が無いのに係数が入っている場合や、終わりの時期が書かれていないのに終了日が入っている場合です。確定は止めませんので、内容を確かめてから進めてください。

指摘は値を直せば消えますが、**直しようのない指摘もあります。** 所見に数量が書かれていないまま見立てを置く場合がそれで、係数を選び直しても「本文に根拠が無い」という事実は変わりません。この場合は指摘の下の **「内容を確認した」** にチェックを入れてください。指摘は記録として残したまま、確認済みとして扱われます。値を変えるとチェックは外れ、もう一度確認を求められます。

所見は**登録した月ではなく、書かれた日付の範囲で使われます。** 月をまたぐ出来事を翌月にも登録すると、係数が掛け合わさって二重に効きます。確定時に警告が出るので、同じ出来事なら片方だけにしてください。

AIを利用できない環境でも、**「手で追加」** から同じ内容を入力できます。予測の補正はAIの有無に依存しません。

レビュー所見では **「日次備考から下書き」** を押すと、その月の日次備考（休業・祝日カレンダーの備考欄）と休業・特別営業の記録をAIが箇条書きに要約し、本文に挿入できます。月末に備考を読み返して書き起こす手間と読み落としを減らすためのものです。予測所見では使えません。対象月は未来なので備考にあるのは計画休業程度で、それは予測が既に織り込んでいます。要約はダイアログで確認・修正してから挿入し、**保存はされません**。備考に書かれていない原因や影響が補われていないか、人名が残っていないかを確かめてから「所見を保存」を押してください。

**「所見メンテナンス」**（485）では、登録済みの所見を一覧して内容を直接編集できます。過去分の修正や、確定の解除（所見を消さずに補正だけ外す）に使います。

### 解析に使うモデルの選び方

所見の解析は 4B〜35B 級のモデルで動作を確認しています。この処理は推論能力より**指示追従**の性質が強く、規模の大きいモデルが有利とは限りません。120B 級で応答が壊れる例も出ています。

モデルを変えるときは、印象ではなく測って決めてください。`bench_remark_parse` が同じサンプルを複数のモデルに流して結果を並べます。

```bash
# 使えるモデルの一覧
docker compose exec web python3 gfdash/manage.py bench_remark_parse --list

# モデルを指定して比較する
docker compose exec web python3 gfdash/manage.py bench_remark_parse \
    --ollama-models <モデル名をカンマ区切り>
```

測定例と読み方は [bench_remark_parse.md](bench_remark_parse.md) にあります。

### 予測の反映先

**来場者数情報**（101）の「予測来場者数」は、実績のある日は実績、実績の無い日は予測バッチの結果を使って着地見込みを描きます。日ごとの曜日・休業・気温、所見による補正まで織り込まれた値になります。

予測バッチを実行していない場合は、当月の平均を並べる従来の方法になります。凡例で区別できます（**予測来場者数（AI）** / **予測来場者数**）。

**来場者予測推移**（410）では、グラフとレポートに加えて、その月の所見が読み取り専用で表示されます。未確定の所見には「予測とレポートには反映されていません」と出ます。

### 実行履歴の比較

予測とレポートの実行は、条件と結果が履歴として保存されます。**「予測実行履歴比較」**（415）で、2つの実行を選んで予測値を重ねて比較できます。

予測は同じ条件なら同じ結果になります（予測値は決定論的に求まり、上下限を作るシミュレーションの乱数も固定しています）。そのため差が出た場合、原因は**実績データの増加・設定変更・休業補正の条件変化・所見の補正**のいずれかに絞れます。実行条件の違いは比較結果にも並べて表示されるので、原因の見当が付けられます。

設定や所見を変えたときに効果があったのかを確かめる用途を想定しています。

### 精度の検証

保存済みの予測を実績と突き合わせ、精度を数で確かめられます。

```bash
# 評価できる実行の一覧
docker compose exec web python3 gfdash/manage.py evaluate_forecast --list

# 2つの実行を指定した月で比較する
docker compose exec web python3 gfdash/manage.py evaluate_forecast \
    --runs 4,8 --month 2026-09 --detail
```

平均誤差率（MAPE）・偏りの向き・予測幅の的中率を出します。複数の実行を指定した
場合は、**両方に実績がある日だけ**で比べ直します。対象日数が違うと、差が精度の差
なのか対象の差なのか分からなくなるためです。

休業日は既定で除外します。休業の影響は休業補正という別の機能が担っており、
所見の効果と混ぜると何を測っているのか分からなくなります。
