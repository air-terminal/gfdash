# AI予測・レポート

来場者数の予測（Prophet）と、月次レポートの自動生成（ローカルLLM）についての
セットアップと使い方です。

**この機能は任意です。** 推論エンジンを用意しなくても、集計・分析の各画面は
そのまま使えます。予測だけを使い、レポートを使わないこともできます。

| 画面 | 内容 |
| :--- | :--- |
| 来場者予測推移（410） | 日別の来場者予測とレポートの表示 |
| 予測実行履歴比較（415） | 過去の予測実行を並べて比較する |
| 月次所見入力（480） | 運営上の出来事を書き、補正の定義へ変換する |
| 所見メンテナンス（485） | 変換された補正定義を確認・修正する |
| AIバッチ手動実行（490） | 予測とレポート生成をその場で実行する |

予測の区分は「平年通り」「天候が良い場合」「天候が悪い場合」の3本です。

---

## 1. 推論エンジンを用意する

レポート生成と所見の解析にローカルLLMを使います。推論エンジンは2つの方式に
対応しています。どちらか一方を用意してください。

| 方式 | `LLM_PROVIDER` | 対象 |
| :--- | :--- | :--- |
| Ollama ネイティブAPI | `ollama`（初期値） | Ollama |
| OpenAI互換API | `openai` | llama.cpp server / vLLM / LM Studio / [FreeToken](https://github.com/FlashML-org/FreeToken) など |

### A. Ollama を使う場合

ローカルにOllamaをインストール・起動し、あらかじめ対象のAIモデルをPull（ダウンロード）しておきます。

```bash
ollama pull gemma4:e4b
```

*(※別のモデル、例えば `qwen2.5:7b` などを使用する場合は、そちらをPullしてください)*

### B. OpenAI互換APIの推論エンジンを使う場合

お使いのエンジンの手順に従って起動し、モデルを読み込んでおきます。導入方法は
製品ごとに異なるため、本システムでは扱いません。本システムが必要とするのは
**OpenAI互換のエンドポイントのURLだけ**です。

起動できたら、接続できるか事前確認しておくとトラブル時の切り分けが楽になります。

```bash
curl http://localhost:8080/v1/models
```

モデルの一覧がJSONで返れば準備完了です。この `/v1` までのURLを
`OPENAI_API_BASE` に設定します。

なお、コンテキスト長と思考の切り替えは**OpenAI互換API推論エンジン側の設定に従います**
（画面やパラメータからは指定できません）。必要な場合はエンジンの起動オプションで
調整してください。

## 2. 設定項目

`.env`（または `gfdash/settings.py`）を環境に合わせて調整します。

### 必ず変更するもの

* **`DISABLE_BATCH_EXECUTION`**: AIバッチ処理（予測やAIレポート生成など）の無効化フラグです。初期値は安全のため `True`（無効）になっています。実際にAI機能を利用する際は、必ず **`False`** に書き換えてください。

### 接続先

* **`LLM_PROVIDER`**: 使用する推論エンジンのAPI方式（初期値: `ollama`）。
  * `ollama` … Ollama のネイティブAPIを使います。従来どおりの動作です。
  * `openai` … OpenAI互換APIを使います。[FreeToken](https://github.com/FlashML-org/FreeToken) / llama.cpp server / vLLM / LM Studio など、OpenAI互換のエンドポイントを提供する推論エンジンで動作します。
  * 互換API側では**コンテキスト長と思考の切り替えをリクエストで指定できません**（推論エンジン側の設定に従います）。該当する入力欄は画面上で無効化されます。
* **`OPENAI_API_BASE`**: OpenAI互換APIの接続先（`LLM_PROVIDER=openai` のとき）。`/v1` まで含めて指定します。
* **`OPENAI_API_KEY`**: 同上の認証キー。ローカルの推論エンジンでは不要なことが多く、空のままで構いません（空の場合は認証ヘッダを送りません）。
* **`OLLAMA_API_URL`**: Ollamaが動作しているエンドポイントのURLを指定します（`LLM_PROVIDER=ollama` のとき）。
  * **DockerコンテナからホストのOllamaを叩く場合**: `'http://host.docker.internal:11434/api/generate'` (初期値)
  * **Dockerを使わず、ローカルPC上で直接システムを実行する場合**: `'http://localhost:11434/api/generate'` に書き換えてください。
* **`OLLAMA_MODEL`**: 使用するAIのモデル名を設定します（初期値: `'gemma4:e4b'`）。方式に関わらず、この項目でモデルを指定します。

### 実行パラメータ

* **`OLLAMA_PRESET`**: AI実行パラメータのプリセット（初期値: `standard`）。通常はこれだけを指定すれば十分です。

  | 値 | 用途 | num_ctx | タイムアウト | 思考 |
  | :--- | :--- | ---: | ---: | :---: |
  | `standard` | 通常はこれ | 4096 | 300秒 | 無 |
  | `long_running` | タイムアウトする場合 | 4096 | 1800秒 | 無 |
  | `low_memory` | モデルが読み込めない、極端に遅い場合 | 2048 | 900秒 | 無 |
  | `high_context` | より多くの実績データを渡したい場合 | 8192 | 900秒 | 無 |
  | `thinking` | 多段の推論をさせる場合 | 16384 | 1800秒 | 有 |

  * 下記の個別設定を書いた場合は、そちらがプリセットより優先されます。プリセットで運用する場合は個別設定をコメントアウトしてください。
  * AIバッチ実行画面(490)からは、実行のたびに一時的に変更することもできます。

* **`OLLAMA_TIMEOUT`**: タイムアウト秒数（初期値: プリセットの値）。CPU実行時などレポート生成に時間がかかる場合は、`600` など長めの値を設定してください。
* **`OLLAMA_NUM_CTX`**: AIが確保する記憶領域のトークン数（初期値: `4096`）。値を上げるとより多くの実績データをプロンプトに含められますが、VRAMの使用量も増えます。モデルが読み込めない場合は `2048` などに下げてください。
  * **`LLM_PROVIDER=openai` では使用されません。** 推論エンジン側の設定に従います。
  * 適切な値はVRAM容量だけでは決まりません。同じ容量でも、小さなモデルなら余裕があり、大規模なモデルでは本体だけでほぼ埋まります。AIバッチ実行画面(490)に症状から選べるプリセットを用意しているので、そちらもご利用ください。
* **`OLLAMA_THINK`**: 思考（thinking）を有効にするかどうか（初期値: `False`）。
  * **`LLM_PROVIDER=openai` では使用されません。** 推論エンジン側の設定に従います。
  * 思考に対応したモデルを使う場合のみ意味を持ちます。非対応のモデルには送信されません。
  * **有効にする場合は `OLLAMA_NUM_CTX` も併せて広げてください。** 思考は与えられたコンテキストを埋めるように消費するため、余裕が無いと本文が生成されないまま終わります（レポートが空になります）。
  * 現在のレポートは集計済みの数値を定型の見出しに沿って記述するもので、多段の推論を必要としません。そのため初期値では無効にしています。

## 3. 動かしてみる

すべてのデータ投入とAIの準備が完了したら、予測・レポート作成処理をテストします。
ブラウザの画面から実行する方法と、コマンドラインから実行する方法があります。

### A. ブラウザ画面から実行する

管理者アカウントでログインし、**「AI予測分析」 → 「AIバッチ手動実行」**（490）を開きます。
ボタンを押すと、バックグラウンドで予測計算やレポート生成が実行され、
ダッシュボードに結果が反映されます。

*(※実行する前に `DISABLE_BATCH_EXECUTION` を `False` に書き換えておく必要があります)*

### B. コマンドラインから実行する

cron へ組み込む場合はこちらを使います。

#### ① Prophetによる来場者数予測

```bash
python manage.py run_forecast --periods 30
```

| オプション | 内容 |
| :--- | :--- |
| `--periods <整数>` | 予測する未来の日数（初期値: `30`） |
| `--output <ファイル名>` | 外部連携用に出力するJSONのファイル名（初期値: `forecast.json`） |
| `--note <文字列>` | 実行履歴に残すメモ。比較画面（415）で実行を見分ける目印になる |
| `--from-ym <YYYY-MM>` | 指定した月の1日から予測をやり直す（学習を前月末までに限定）。月の途中で実行しても、その月全体が予測になる（`--periods` がその月の日数に満たなければ月末まで延ばす）。補正の効果を比べるときに基準をそろえる用途 |

`--from-ym` の月によって、結果の行き先が変わります。

| 起点 | 扱い | 実行履歴（415で比較） | 最新予測（101・ラズパイ同期） |
| :--- | :--- | :--- | :--- |
| 実行月以降 | 最新予測の更新 | 残す | **置き換える** |
| 実行月より前 | 過去の打ち直し | 残す | **触らない** |

過去の月を打ち直す目的は精度の評価です。運用中の最新予測を古いデータで学習した予測で
置き換える理由が無いため、履歴だけを残します。`evaluate_forecast --runs <ID>` でその月を
評価できます。

**計画休業の反映について:**
休業・祝日カレンダー（画面913）で「計画」として登録された時間帯休業は、
予測値に営業時間ぶんの補正が掛かります。終日休業なら 0 になります。
補正の割合は自社の過去実績から自動で算出されるため、設定は不要です。
実績が少ない環境では時間帯の単純按分にフォールバックします。

台風接近などの天候起因で登録された休業は、将来について予見できないため
補正の対象外です。この区別は `temp_closed` のビットで行っています
（[codes.md](codes.md) を参照）。

#### ② ローカルLLMによるレポート生成

```bash
python manage.py run_llm_analysis --mode review
```

| オプション | 内容 |
| :--- | :--- |
| `--mode <review \| forecast_1m \| forecast_3m>` | **【必須】** レポートの種類。`review`:当月の振り返り / `forecast_1m`:翌月の予測 / `forecast_3m`:3ヶ月先までの予測 |
| `--ym <YYYY-MM>` | 分析・予測の基準となる年月（初期値: 実行時の当月） |
| `--model <モデル名>` | 一時的に別のモデルを指定して実行する |
| `--stream` | 生成の様子をコマンドライン上にリアルタイム表示する |

## 4. 使い方

セットアップが済んだあとの、日常運用の流れです。画面は「AI予測分析」メニューに
まとまっています。

### 月次所見 — AIが知らない情報を渡す

競合店の開業、近隣の工事、設備の入れ替えなど、**実績データに現れる前から分かっている出来事**があります。これらは過去のデータから学習できないため、予測にもレポートにも反映されません。

**「月次所見入力」**（480）で、対象月を選び、タブで区分を切り替えて自由文を書きます。

| 区分 | 用途 | 使われる先 | 手順 |
| :--- | :--- | :--- | :--- |
| 予測所見 | これから先を見通すための情報 | 予測の補正と予測レポート | 保存 → AIで解析（または手で追加）→ 確定 |
| 振り返り所見 | 済んだ月に実際に起きたこと | 振り返りレポートのみ | 保存 → 確定 |

振り返り所見は本文だけで、補正の設定はありません。起きたことは実績に出ているため、見立てを置く意味が無いからです。先の月に影響が続く出来事は、予測所見のほうに書いてください。

以下は予測所見の手順です。押せる順にしかボタンが有効にならないので、迷うことはありません。

**「AIで解析」** は自由文を補正の形へ変換します。イベントごとに種別・期間・影響の見立てを読み取り、表に並べます。

* 影響の見立ては「大きく増える（+20%）」〜「大きく減る（-20%）」から選びます。`%` で直接指定することもできます。係数は通常を `1.00` とした倍率で、幅は見立ての不確かさを表します
* 影響が読めない出来事は種別を「記録のみ」にします。レポートの材料にはなりますが、予測の補正には使われません
* **根拠・補足情報は必須です。** 半年後に妥当性を見直せるようにするためです

**確定した所見だけが予測とレポートに使われます。** AIが出した数値をそのまま予測へ流さないための一段です。

所見の本文から導けない値があると「要確認」が表示されます。たとえば所見に数量の記載が無いのに係数が入っている場合や、終わりの時期が書かれていないのに終了日が入っている場合です。確定は止めませんので、内容を確かめてから進めてください。

指摘は値を直せば消えますが、**直しようのない指摘もあります。** 所見に数量が書かれていないまま見立てを置く場合がそれで、係数を選び直しても「本文に根拠が無い」という事実は変わりません。この場合は指摘の下の **「内容を確認した」** にチェックを入れてください。指摘は記録として残したまま、確認済みとして扱われます。値を変えるとチェックは外れ、もう一度確認を求められます。

所見は**登録した月ではなく、書かれた日付の範囲で使われます。** 月をまたぐ出来事を翌月にも登録すると、係数が掛け合わさって二重に効きます。確定時に警告が出るので、同じ出来事なら片方だけにしてください。

AIを利用できない環境でも、**「手で追加」** から同じ内容を入力できます。予測の補正はAIの有無に依存しません。

振り返り所見では **「日次備考から下書き」** を押すと、その月の日次備考（休業・祝日カレンダーの備考欄）と休業・特別営業の記録をAIが箇条書きに要約し、本文に挿入できます。月末に備考を読み返して書き起こす手間と読み落としを減らすためのものです。予測所見では使えません。対象月は未来なので備考にあるのは計画休業程度で、それは予測が既に織り込んでいます。要約はダイアログで確認・修正してから挿入し、**保存はされません**。備考に書かれていない原因や影響が補われていないか、人名が残っていないかを確かめてから「所見を保存」を押してください。

**「所見メンテナンス」**（485）では、登録済みの所見を一覧して内容を直接編集できます。過去分の修正や、確定の解除（所見を消さずに補正だけ外す）に使います。

### 解析に使うモデルの選び方

所見の解析は 4B〜35B 級のモデルで動作を確認しています。この処理は推論能力より**指示追従**の性質が強く、規模の大きいモデルが有利とは限りません。120B 級で応答が壊れる例も出ています。

モデルを変えるときは、印象ではなく測って決めてください。`bench_remark_parse` が同じサンプルを複数のモデルに流して結果を並べます。

```bash
# 使えるモデルの一覧
docker compose exec web python3 gfdash/manage.py bench_remark_parse --list

# モデルを指定して比較する
docker compose exec web python3 gfdash/manage.py bench_remark_parse \
    --ollama-models <モデル名をカンマ区切り>
```

測定例と読み方は [bench_remark_parse.md](bench_remark_parse.md) にあります。

### 予測の反映先

**来場者数情報**（101）の「予測来場者数」は、実績のある日は実績、実績の無い日は予測バッチの結果を使って着地見込みを描きます。日ごとの曜日・休業・気温、所見による補正まで織り込まれた値になります。

予測バッチを実行していない場合は、当月の平均を並べる従来の方法になります。凡例で区別できます（**予測来場者数（AI）** / **予測来場者数**）。

**来場者予測推移**（410）では、グラフとレポートに加えて、その月の所見が読み取り専用で表示されます。未確定の所見には「予測とレポートには反映されていません」と出ます。

### 実行履歴の比較

予測とレポートの実行は、条件と結果が履歴として保存されます。**「予測実行履歴比較」**（415）で、2つの実行を選んで予測値を重ねて比較できます。

予測は同じ条件なら同じ結果になります（予測値は決定論的に求まり、上下限を作るシミュレーションの乱数も固定しています）。そのため差が出た場合、原因は**実績データの増加・設定変更・休業補正の条件変化・所見の補正**のいずれかに絞れます。実行条件の違いは比較結果にも並べて表示されるので、原因の見当が付けられます。

設定や所見を変えたときに効果があったのかを確かめる用途を想定しています。

### 精度の検証

保存済みの予測を実績と突き合わせ、精度を数で確かめられます。

```bash
# 評価できる実行の一覧
docker compose exec web python3 gfdash/manage.py evaluate_forecast --list

# 2つの実行を指定した月で比較する
docker compose exec web python3 gfdash/manage.py evaluate_forecast \
    --runs 4,8 --month 2026-09 --detail
```

平均誤差率（MAPE）・偏りの向き・予測幅の的中率を出します。複数の実行を指定した
場合は、**両方に実績がある日だけ**で比べ直します。対象日数が違うと、差が精度の差
なのか対象の差なのか分からなくなるためです。

休業日は既定で除外します。休業の影響は休業補正という別の機能が担っており、
所見の効果と混ぜると何を測っているのか分からなくなります。
